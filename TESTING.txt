NETUNIM TESTING
===============

One-time setup (repository root)
-------------------------------
Python 3.10+, Node 22.13+/24+, and Chrome, Edge or Chromium are required.
This refactor was checked with Node 24 and Python 3.14 on Windows.

  python -m pip install -r tests/requirements.txt
  npm ci

npm development tools use semver ranges in package.json and exact resolved versions in package-lock.json;
none are deployed or imported at runtime. Use npm ci for reproducible setup. No bundler is required. Native ESM requires localhost/HTTPS; file:// and isolated-document fallbacks are unsupported.

Commands
--------
  verify.bat
  verify.bat --no-pause
  python tests/run_all.py
  npm run lint
  npm run updates:check
  npm run deps:update
  npm run wrangler:check
  npm run wrangler:update
  node --test tests/business_models.test.mjs tests/shared_contracts.test.mjs tests/sync_models.test.mjs tests/storage_models.test.mjs

After changing a public asset or canonical shared source:
  python tools/sync-assets.py
  verify.bat --no-pause

The cache name intentionally changes for real public-content changes. Checkout-only LF/CRLF differences do not
change it. Verification checks drift without modifying files. Both deployment scripts run this complete gate first.
For safe deployment-path verification without Wrangler or upload:
  netunim-kupa\deploy_site.bat --preflight-only
  netunim-orders\deploy_site.bat --preflight-only
  deploy_all.bat --preflight-only

For a paired production release, use deploy_all.bat. It runs the complete repository verifier once,
then applies the site-specific deployment guards and upload for both applications. Running each
individual deploy_site.bat separately remains supported, but each standalone deployment correctly
runs the repository verifier for itself.


Dependency updates
------------------
Run npm run updates:check to check both package.json development dependencies and Wrangler.
For normal npm minor/patch updates within the declared major ranges, run npm run deps:update, then
verify.bat --no-pause. Major npm upgrades remain deliberate: install the reviewed @latest version explicitly,
then run the full verifier before keeping the lockfile change.

Wrangler is intentionally not a package.json dependency because deployment executes it only inside a fresh,
isolated temporary directory. Its single reproducible deployment version lives in tools/wrangler-version.txt.
Use npm run wrangler:check to compare it with npm, and npm run wrangler:update to update within the current
major. A future Wrangler major version requires the explicit npm run wrangler:update-major command after
reviewing the migration/release notes. Never replace the deployment pin with wrangler@latest: a new CLI release
must not silently change production deployment behavior before verification.

Suites
------
static_contracts.py: syntax, SQL/RPC, ownership, financial sequencing and deployment gates.
asset_contracts.py: ESM entry, inert/empty seed, CSP and zero inline executable event attributes.
deploy_preflight.py: read-only public file allowlist, blocked directories, size and secret scans.
service_worker_contracts.py: complete shell, install/activate, app-scoped cleanup, network-first and cache-scoped
  offline fallback that rejects conflicting assets from unrelated origin caches.
module_contracts.py: deterministic shared copies/cache manifest, normalized cross-platform text hashing,
  byte-exact binary hashing, read-only/idempotent generation, acyclic local module graph, layer boundaries,
  no runtime globals/test APIs, pinned ESLint rules and direct Node tests.
runtime_smoke.py: boot, tabs, lists and scroll restoration in real Chromium.
runtime_events.py: delegated actions, keyboard, focus/blur dates, series, draft guard, bulk and drag/drop.
runtime_security.py: hostile business fields and IDs in lists, selectors and modal HTML under production CSP.
runtime_workflows.py: create/edit/delete, financial/check flows, inventory/reservations, notes and file restore.
runtime_pwa.py: uninstrumented ESM, real SW installation, all cached modules, offline reload/recovery,
  preserved pending and actual second-tab Web Locks protection; upgrades each historical worker fixture in place,
  verifies current cached bytes and local HTTP security headers/MIME, poisons an older unrelated cache with fake
  app.js/index.html responses, then restarts Chromium with no HTTP response and proves the current cache wins.
runtime_performance.py: eight renders of 1,000 records; bounded time, stable listeners and no render-time writes/RPC.
runtime_data_integrity.py: backup round-trip, wrong formats/future schemas, cloud ownership and merge.
runtime_sync_recovery.py: offline persistence, resume, independent edits, same-record conflicts and revision retry.
runtime_financial.py: deposit/return/delete deltas, watermarks, pending effects and shared-check bootstrap repair.

Direct module tests
-------------------
Business models cover credit cents/dates, recurrence, bank effects, supplier/customer balances, service precedence,
inventory receipts/reservations, normalization and portable restore validation. Merge tests cover optional fields,
independent edits, delete/edit conflicts, in-flight rebase, pending freshness and shared RPC request/revision validation.
Storage tests use in-memory File System Access handles to exercise verified writes, corruption, permission denial,
serialized writes and preservation of pre-existing folder data. They do not write user folders.

Isolation and limits
--------------------
Browser tests copy site/ into temporary directories, use disposable Chromium profiles and replace public cloud
configuration with fake endpoints. Production data, credentials, database and deployment are never contacted.
Most integration suites instrument ONLY these temporary copies with lexical test access via module_probe.cjs.
The shipped modules contain no test hooks or global compatibility bridge. runtime_pwa.py uses no module instrumentation.
Actual localhost navigation and asynchronous appReady completion are required; a failed startup does not fall back
to a simulated DOM. Real CSP headers are served by the harness. Browser-initiated downloads exercised by workflows
are redirected into each disposable runtime directory and deleted with that session; tests must never write the user's
real Downloads folder. Browser tests require an available loopback port.

Performance limits catch pathological regressions, not small machine-dependent timing differences. Headless tests
and fake file handles cannot certify native folder-picker UI, installation on every OS, live Supabase/RLS, Access
policies or a production rollout. Check those separately with authorized accounts and data before release.
The compatibility scripts under netunim-orders/supabase/shared/validation remain thin forwarding entrypoints.
