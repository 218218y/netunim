NETUNIM TESTING
===============

One-time setup (repository root)
-------------------------------
Python 3.10+, Node 22.13+/24+, and Chrome, Edge or Chromium are required for the normal local workflow.
This refactor was checked with Node 24 and Python 3.14 on Windows.

Normal local setup:
  python -m pip install -r tests/requirements.txt
  npm ci
  python tools/install-git-hooks.py

The last command installs the repository-managed pre-commit hook. GitHub Desktop runs it automatically when
creating a commit. The installer pins the verified absolute Python path, so this hook does not depend on GitHub
Desktop successfully loading PATH from the configured shell. Rerun the installer if Python is moved or reinstalled.
The hook runs sync-assets.py against the exact staged/index snapshot, stages only its generated shared copies and
service-worker metadata, and also refreshes the working tree. This preserves unchecked files and partially staged
content instead of accidentally adding them to the commit. Verify or repair the local installation at any time with:
  npm run hooks:check
  npm run hooks:install

This is intentionally a pre-commit hook rather than pre-push: at pre-push time the commit already exists, so an
automatic repair would not be part of the version uploaded to GitHub. CI keeps the read-only --check gate as the
authoritative backstop. GitHub Desktop can bypass commit hooks, but that should be reserved for diagnosing a broken
local Python/hook installation; the CI check will still reject unsynchronized assets.

The ChatGPT offline installer uses a content-addressed cache outside the repository (by default
`~/.cache/netunim/offline/...` on the Linux repair host); it never uses or replaces the normal root `node_modules`.
`NETUNIM_OFFLINE_CACHE_DIR` may override the cache base, but repository-internal paths are rejected.
The Windows launchers also suppress `serve`'s nonessential network update notification so a registry/network problem
does not delay local startup. For the equivalent manual PowerShell debug launch use:
  $env:NO_UPDATE_CHECK='1'; npx serve . --debug
This setting is process-local; the launchers use `setlocal` and do not change the user's global Windows/npm settings.

ChatGPT/Linux offline setup (preferred for repair sessions):
  npm run offline:download

Run `offline:download` once on an internet-connected machine before uploading the repository. It stores only
the Linux x86_64/glibc Node runtime, the exact npm verification closure from package-lock.json, and the
websocket-client wheel required by the browser harness. Browser binaries are supplied separately by the host.
After upload, first verify both the package vendor and the host browser capability:
  npm run offline:check
  npm run offline:doctor

For ChatGPT repair sessions use:
  npm run test:chat

`test:chat` runs the full gate when localhost/CDP works. If the host browser is installed but blocked by an
enterprise URL policy, it runs the deterministic non-browser core suites and clearly reports that runtime suites
were skipped. This fallback is for repair feedback only. The strict deployment-grade command remains:
  npm run test:offline

If an unmanaged test browser is available, point the harness to it before running doctor/tests:
  NETUNIM_BROWSER=/path/to/chrome-for-testing npm run offline:doctor

npm development tools use semver ranges in package.json and exact resolved versions in package-lock.json;
none are deployed or imported at runtime. No bundler is required. Native ESM requires localhost/HTTPS; file://
and isolated-document fallbacks are unsupported.

Local parallel verification
---------------------------
verify.bat, npm test, and the normal deployment BAT files use the same complete suite inventory.
The local runner now overlaps independent suites by default: half the available logical CPUs, capped at 4
concurrent suites (minimum 1). At most 2 browser suites and 1 database suite run together. The performance
suite runs alone so other verification suites do not distort its render measurements. Long independent
Morning, browser/database, and module suites start early. No suite, assertion, or test result is cached or skipped.

Use --jobs 1 for the original serial order, --jobs N for an explicit limit, and --browser-jobs 1 to reduce
browser load. To configure the existing BAT files in PowerShell without changing them:
  $env:NETUNIM_VERIFY_JOBS = '2'
  .\verify.bat --no-pause
  Remove-Item Env:NETUNIM_VERIFY_JOBS
The limit counts suite processes; an individual suite can itself start several browser/Node processes.
GitHub --group runs still default to 1 suite at a time within each separate matrix machine, even when
NETUNIM_VERIFY_JOBS is set. Explicit --jobs overrides either default. --group and --core-only remain partial gates.

Local runs save per-suite logs, results.json, junit.xml and summary.md in a unique .work/verification/ directory.
--report-dir chooses a different report location; --verbose prints successful logs as well as saving them.
The console shows starts, results, and progress every 15 seconds. JSON records wall time and each suite's
start/end offset; summed suite seconds can exceed elapsed time during parallel execution.
On failure, already running suites finish and queued suites remain explicitly not-run. --keep-going runs
the rest and still returns failure. Ctrl+C and suite timeouts stop owned processes and retain failure reports.
Windows Job Objects contain the suite's descendants (including Chromium's nested jobs) and wait for their
termination; POSIX uses separate process groups. Each suite has its own temporary directory, browser profiles,
loopback ports, and disposable database. Running suites never share a test database or browser profile.
On Windows, the browser harness keeps a dedicated host-state seed under `.work/browser-host-state/`, keyed to the
current user, machine and selected Chrome/Edge executable. Its first boot uses a dedicated test profile. Chromium
does not populate its OS password-check preferences merely by starting, so the harness obtains the OS password
change time through Windows `NetUserGetInfo` without making a login attempt. It sets the conservative nonblank
value and writes only `password_manager.os_password_blank` and `password_manager.os_password_last_changed` to each
new disposable profile's `Local State`. No Default profile, cookies, LocalStorage, IndexedDB, service workers or
application data are copied or shared. The seed bootstrap is locked across suite processes and is never removed
by session cleanup. A failed bootstrap is recorded and later browser launches stop with an error; fix the cause
before removing the affected seed directory to retry. `NETUNIM_BROWSER` remains supported and has its own seed.
Do not start installed Chrome/Edge with a fresh `--user-data-dir` in ad-hoc tests; use `BrowserSession` so this
Windows host-state preparation and the disposable profile isolation are both applied.
Cleanup handles Windows read-only attributes inherited by copytree, including read-only directories: the
attribute is cleared only on the failing temporary copy, never on the repository's original site files.
Reports contain diagnostics only and are never accepted as deployment approval or reused as passing results.
Morning's document matrix uses a distinct debt for each independent case. Replacing a debt's progress while
reusing its ID would conflict with the real append-only outbox merge. A controlled old acknowledgement is
held across a case boundary to test that isolation deterministically, without disabling cloud synchronization.

After changing a public asset or canonical shared source:
  python tools/sync-assets.py
  verify.bat --no-pause

The cache name intentionally changes for real public-content changes. Checkout-only LF/CRLF differences do not
change it. Verification checks drift without modifying files. The normal deployment scripts run this complete gate first.
GitHub Actions and the separate *_fast.bat entrypoints are documented in CI_DEPLOYMENT.md.
For safe deployment-path verification without Wrangler or upload:
  netunim-kupa\deploy_site.bat --preflight-only
  netunim-orders\deploy_site.bat --preflight-only
  deploy_all.bat --preflight-only

For a paired production release, use deploy_all.bat. It runs the complete repository verifier once,
then applies the site-specific deployment guards and upload for both applications. Running each
individual deploy_site.bat separately remains supported, but each standalone deployment correctly
runs the repository verifier for itself.


Dependency updates
------------------
Run npm run updates:check to check both package.json development dependencies and Wrangler.
For the ChatGPT offline bundle, `npm run offline:update` is the canonical maintenance command: it updates the npm
lockfile within the reviewed package.json ranges, advances the pinned websocket-client release within >=1.8,<2,
stages and verifies the complete replacement bundle, atomically swaps it into vendor/offline, and only then deletes
superseded offline archives. If metadata/download fails, package-lock.json and tools/offline-deps.json are restored.
The Node 24 archive remains an explicit reviewed pin rather than silently following a new runtime release.

For a normal non-offline npm workspace you may still run npm run deps:update, then verify.bat --no-pause. Major npm
upgrades remain deliberate: install the reviewed @latest version explicitly, then run the full verifier before
keeping the lockfile change.

Wrangler is intentionally not a package.json dependency because deployment executes it only inside a fresh,
isolated temporary directory. Its single reproducible deployment version lives in tools/wrangler-version.txt.
Use npm run wrangler:check to compare it with npm, and npm run wrangler:update to update within the current
major. A future Wrangler major version requires the explicit npm run wrangler:update-major command after
reviewing the migration/release notes. Never replace the deployment pin with wrangler@latest: a new CLI release
must not silently change production deployment behavior before verification.

  no runtime globals/test APIs and pinned ESLint rules.
node_models.py: all tests/*.test.mjs files discovered automatically, with two isolated Node workers.
verification_plan.py: one complete suite inventory for local full verification and the GitHub Actions matrix.
runtime_sync_postgres.py: real browser/HTTP/PostgreSQL synchronization, lost acknowledgements and merge conflicts.
runtime_browser_isolation.py: real same-origin LocalStorage/IndexedDB separation and disposable profile cleanup.

runtime_events.py: delegated actions, keyboard, focus/blur dates, series, draft guard, bulk and drag/drop.

runtime_workflows.py: create/edit/delete, financial/check flows, inventory/reservations, notes and file restore.
runtime_pwa.py: uninstrumented ESM, real SW installation, all cached modules, offline reload/recovery,

runtime_performance.py: eight renders of 1,000 records; bounded time, stable listeners and no render-time writes/RPC.
runtime_data_integrity.py: backup round-trip, wrong formats/future schemas, cloud ownership and merge.

Direct module tests
-------------------
Business models cover credit cents/dates, recurrence, bank effects, supplier/customer balances, service precedence,
inventory receipts/reservations, normalization and portable restore validation. Merge tests cover optional fields,
independent edits, delete/edit conflicts, in-flight rebase, pending freshness and shared RPC request/revision validation.
Storage tests use in-memory File System Access handles to exercise verified writes, corruption, permission denial,
serialized writes and preservation of pre-existing folder data. They do not write user folders.

Isolation and limits
--------------------
Browser tests copy site/ into temporary directories, use disposable Chromium profiles and replace public cloud
configuration with fake endpoints. Production data, credentials, database and deployment are never contacted.
Most integration suites instrument ONLY these temporary copies with lexical test access via module_probe.cjs.
The shipped modules contain no test hooks or global compatibility bridge. runtime_pwa.py uses no module instrumentation.
Actual localhost navigation and asynchronous appReady completion are required; a failed startup does not fall back
to a simulated DOM. Real CSP headers are served by the harness. Browser-initiated downloads exercised by workflows
are redirected into each disposable runtime directory and deleted with that session; tests must never write the user's
real Downloads folder. Browser tests require an available loopback port and a browser allowed to navigate to localhost. A browser merely
being installed is insufficient; `offline:doctor` checks the real capability. `NETUNIM_BROWSER` is the supported
way to select a dedicated unmanaged test browser.

Performance limits catch pathological regressions, not small machine-dependent timing differences. Headless tests
and fake file handles cannot certify native folder-picker UI, installation on every OS, live Supabase/RLS, Access
policies or a production rollout. Check those separately with authorized accounts and data before release.
The compatibility scripts under netunim-orders/supabase/shared/validation remain thin forwarding entrypoints.
