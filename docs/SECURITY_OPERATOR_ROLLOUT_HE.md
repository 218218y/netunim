# הוראות השלמת ההקשחה בשלושת המחשבים

עודכן ב־10 בנובמבר 2026. דוח המצב הטכני נמצא ב־`SECURITY_COMPLETION_20261109_HE.md`.

## 1. לפני העדכון

פתח את שתי המערכות בכל מחשב וודא שהשמירות הסתיימו ושהסנכרון לענן תקין.
אם יש עבודה מקומית שטרם עלתה, שמור גיבוי מוצפן לפני החלפת גרסאות.
אין למחוק את נתוני הדפדפן, קובצי ההצמדה או תיקיות ה־Bridge כחלק מעדכון רגיל.

## 2. עדכון הקוד בכל מחשב

פתח מסוף בתיקיית המאגר באותו מחשב:

```powershell
git status --short
git fetch origin --prune
git switch main
git pull --ff-only origin main
```

אם הפקודה הראשונה מציגה שינויים שלך, שמור אותם לפני החלפת הענף; אין להריץ
`reset --hard` או למחוק אותם. ניקוי ענפים ב־GitHub אינו מעדכן אוטומטית עותקים
מקומיים במחשבים האחרים. אין צורך ליצור ענף חדש לשימוש רגיל במערכת.

## 3. התקנה מחדש של שני המחברים בכל מחשב שמשתמש בהם

הרץ מתוך הקוד המעודכן:

1. Bank Bridge **80** באמצעות `netunim-kupa\bank-bridge\install_bank_bridge.bat`.
2. Document Bridge **48** באמצעות `netunim-orders\document-bridge\install_document_bridge.bat`.

מתחילים במחשב אחד. רושמים את מזהה ה־commit של חבילת ההתקנה ומודדים בו Baseline
לפני החלפת המחברים. לאחר ההתקנה בודקים שהאתרים טענו את גרסת ה־Service Worker
העדכנית. כל מתקין דורש `pairingProtocol: 1` ומשווה את מזהה ההתקנה לזה שהמאזין
קלט בהפעלה. לבדיקה חוזרת מריצים `--check-running` עם פקודת Node הפרטי
שמופיעה במדריך ההצמדה.

משיכת Git לבדה אינה מחליפה את עותק התוכנה המותקן ואת פריטי ההפעלה של Windows.
המתקינים משתמשים ב־Node פרטי ומאומת; אין צורך להחליף ידנית את Node הכללי במחשב.
יש להמתין להצלחת בדיקות המתקין. אם הוא מציג כישלון, אין להתעלם ממנו או להפעיל
ידנית עותק ישן במקביל.

מתקין Document Bridge מציג את היקף החיפוש גם בעדכון של התקנה קיימת. אפשר
לבחור מספר תיקיות, את תיקיית המשתמש (כולל הורדות), או לאשר כוננים מקומיים שלמים.
אפשר להוסיף תיקיית Drive שמופיעה במחשב ובאינדקס Everything. בחירה בכונן שלם
מרחיבה גם את הגישה לפתיחה ולהעברה לסל המיחזור של קבצים בודדים דרך האתר.
למחיקת תיקיות השתמש בסייר Windows. תיקיות מערכת ותוכנות, נתוני המחברים
וקבצים מוסתרים מוחרגים. לשינוי הרשימה המקומית הרץ
`netunim-orders\document-bridge\configure_document_bridge.bat` ופעל לפי הבורר.
ללא תיקיות מורשות חיפוש וקבצים ייחסמו בכוונה.

לאחר בדיקת ה־Origins המדויקים, מבצעים בכל מחבר את המעבר המתואר
ב־[מדריך ההצמדה](BRIDGE_SCOPED_PAIRING_DESIGN_20261109.md). מריצים
`--pairing status` ופותחים חפיפה של עד שבעה ימים עם `--pairing begin`.
מפיקים קוד חד־פעמי עם `--pairing issue` לכל אתר שנדרש למחבר, מעניקים רק
את ההרשאות הדרושות ומזינים את הקוד בדף האבטחה של אותו Origin. הקובץ
`bridge-token.txt` משמש לתאימות ישנה ולשחזור המתועד. שומרים קודים ומפתחות
במחשב המקומי ומחוץ לדוחות התמיכה.

### קבלת המחשב הראשון

- **הצמדה והרשאות.** בודקים פעולות קריאה ורענון לפי ההרשאות של כל אתר.
  בסביבת בדיקה מקומית בודקים שמפתח קריאה אינו מורשה למחוק, שביטול מפתח
  חוסם גם שימוש במזהה מסמך שכבר פורסם, ושמפתח האתר השני ממשיך לעבוד.
  לאחר קבלת שני האתרים מריצים `--pairing finish`, מוודאים מצב `scoped`
  ובודקים שהמפתח הישן נדחה. חוזרים על בדיקת הפעולות עם המפתחות הנפרדים.
- **מסמכים וביצועים.** משתמשים באותה תוכנית ובאותו סוג אימות לפני העדכון
  ואחריו. מודדים בנפרד פתיחה קרה ולפחות 20 חזרות חמות לכל תרחיש. כוללים
  חיפוש שם ותוכן ב־C: וב־Y:, עמוד ראשון ועמודים נוספים, תוצאות רבות,
  קבצים מוסתרים, PDF רגיל ואינטראקטיבי, Word ו־Excel, ו־Y: איטי או מנותק.
  משווים P50 ו־P95. אם P95 עלה בעקביות ביותר מ־20%, עוצרים את הרחבת
  הפריסה וחוקרים במחשב הראשון. [מפרט המדידה](DOCUMENT_BRIDGE_MEASUREMENT_20261109.md)
- **בנק ואשראי.** מרעננים חיבור הפועלים קיים ובודקים תנועות ויתרות.
  בודקים CAL ו־MAX מול נתוני הספק, כולל זיכויים, תשלומים, עסקאות ממתינות
  וסופיות ופרטי מבצע ב־MAX כשיש עסקה מתאימה. מרעננים שוב ובודקים שאין
  כפילויות ושסכומי החיוב תואמים. משתמשים בפרופילים ובהיסטוריה הקיימים.

רק לאחר קבלת המחשב הראשון מעדכנים את שני המחשבים האחרים.

ההתקנה הרגילה מיועדת לכתובות הייצור המורשות. אם מחשב מפעיל את ממשק האתר דרך
`localhost` או `127.0.0.1`, יש לאשר במפורש את ה־Origin המדויק שלו, כולל הפרוטוקול
והפורט שמופיעים בשורת הכתובת. אין לאשר wildcard או כתובת Preview.
ב־Bank Bridge ההגדרה נמצאת ב־`%LOCALAPPDATA%\NetunimKupaBankBridge\origin-policy.json`
עם `version: 1`, מצב `allowlist` ורשימת `allowedOrigins`; ב־Document Bridge מוסיפים
אותו לרשימת `allowedOrigins` ב־`%LOCALAPPDATA%\NetunimDocumentBridge\config.json`,
תוך שמירת רשימת התיקיות והמקורות המורשים הקיימים. אין להחליף הגדרות אלה ברשימה
של מקורות מקומיים בלבד. יש להפעיל מחדש את המחברים לאחר העדכון.
אם נשארו בתצורת Document ערכי wildcard ישנים, החלף אותם במקורות הייצור המדויקים:
`https://orders.bargig-furniture.com`, `https://kupa.bargig-furniture.com`,
`https://bargig-orders.pages.dev` ו־`https://bargig-kupa.pages.dev`, והוסף את הכתובת
המקומית המדויקת. פעולה זו משנה רק את `allowedOrigins`; אין למחוק את `roots`.
לשימוש ב־Morning וב־Google מהממשק המקומי נדרשת גם הוספת אותו Origin בסודות השרת
`FINANCIAL_EDGE_ALLOWED_ORIGINS` ו־`GOOGLE_OAUTH_ALLOWED_ORIGINS`, בהתאמה, תוך
שמירת הערכים התקינים הקיימים. אם משתמשים בכתובות הייצור שבדפדפן, תוספת זו אינה נדרשת.
לאחר שינוי סודות אלה יש לפרוס מחדש את ארבע פונקציות השרת מהקוד התקין ב־main
כדי שכל המופעים ייטענו עם ההגדרה החדשה; אין צורך לשנות סודות בנק או מפתחות הצפנה.

## 4. הפעלת MFA פעם אחת בחשבון, לאחר פריסת שני האתרים

תחילה ודא שבכל שלושת המחשבים נטענה גרסת האתר החדשה, ובמסך ההתחברות מופיע
שדה קוד מאפליקציית אימות. לאחר מכן:

1. פתח [אבטחת החשבון בניהול ההזמנות](https://orders.bargig-furniture.com/security.html)
   או [אבטחת החשבון בקופה](https://kupa.bargig-furniture.com/security.html).
2. התחבר באימייל ובסיסמה הקיימים ובחר **הוסף אפליקציית אימות**.
3. ה־QR והמפתח מופיעים אחרי לחיצה על **הוסף אפליקציית אימות**. אם התמונה אינה
   זמינה, מפתח ההגדרה עדיין מופיע. אם זו
   הפעלה ראשונה, השאר את שדה הקוד ריק במסך ההתחברות. אפשר לסרוק את ה־QR,
   או לפתוח ב־Google Authenticator את **+ → Enter a setup key**, לתת שם
   לחשבון, להזין את המפתח שמופיע מתחת ל־QR ולבחור **Time based**.
   האפליקציה ו־TOTP כלולים ללא תשלום. הקוד נוצר באפליקציה גם בלי חיבור סלולרי.
   שמור אפשרות שחזור או עותק מוצפן/לא־מקוון של המפתח במקום נפרד ממחשבי המחברים.
4. הזן קוד בן שש ספרות ובחר **אמת והפעל**. הודעת הצלחה היא האישור שהרישום הושלם.
5. התחבר מחדש בכל אתר ובכל מחשב עם הסיסמה וקוד האימות. הפעלת גורם חדש עשויה
   לסיים התחברויות קיימות. הפעל שעון אוטומטי בטלפון אם קודים תקינים נדחים.

זהו אותו חשבון Supabase בשתי המערכות; אין צורך להירשם בנפרד בכל מחשב.
הקוד משתנה — אין לשמור קוד חד־פעמי כתחליף לאפליקציה. לאחר ההפעלה, סיסמה בלבד
לא תספיק גם לקריאה ישירה לטבלאות, ל־RPC ולתמונות שיקים פרטיות.

אבד הטלפון וכל אפשרויות השחזור? בעל פרויקט Supabase צריך לאמת את זהות הבעלים
ולאפס את גורם ה־MFA דרך ניהול Auth. אין מנגנון עוקף באתר ואין קוד שחזור קבוע
שהסוכן יצר. אין להסיר גורמים מאומתים כחלק מתחזוקה רגילה.

## 5. סביבת בדיקות ו־Preview

פרויקט הייצור הוא `bupoidcurcxuypfrjqio`; פרויקט הבדיקות הנפרד הוא
`nckszremdktftbhimgxc` (`netunim-staging`) באותו ארגון. הרשמה ציבורית חסומה.
בנייה חדשה ל־Preview בוחרת Staging, וכתובות Preview של שני פרויקטי Pages מוגנות
גם ב־Cloudflare Access. כדי לצפות בהן יש להיכנס עם חשבון הבעלים המורשה.

אין להעתיק ל־Staging מידע אמיתי, פרטי בנק, אסימוני Google או סודות Morning
של הייצור. לבדיקת ספק אמיתי יש להגדיר OAuth Client נפרד ופרטי Morning Sandbox
נפרדים. עד אז חיבורים אלה בסביבת הבדיקות נשארים לא מוגדרים בכוונה.

## 6. בדיקות Windows וגיבויים בכל אחד משלושת המחשבים

בדוק בהגדרות Windows שהדיסק מוצפן באמצעות BitLocker או הצפנת מכשיר, שחשבון
המשתמש מוגן, שיש נעילת מסך אוטומטית וש־Microsoft Defender מעודכן.
שמור גיבויים מוצפנים, כולל גיבוי לשחזור מפתחות הענן אצל הבעלים.
DPAPI נקשר לחשבון Windows; העתקת קובץ מוצפן למחשב אחר אינה גיבוי נייד שמבטיח שחזור.
אין למחוק פרופיל Windows ישן לפני שמירת גיבוי ניתן לשחזור.

אם בעבר שיתפת דוחות התקנה, אבחון או מפתחות הצמדה, נקה עותקים מיותרים והחלף
את המפתח המקומי וההצמדה לפי נוהל תחזוקה. אבחון חדש מצומצם ופג תוקף אוטומטית;
דוחות ישנים שיוצאו בנפרד אינם נמחקים מעצמם.

## מגבלות שנשארות

נשארנו במסלול Supabase Free לפי החלטת הבעלים. הגנת סיסמאות שדלפו לא הופעלה
משום שהשירות דרש שדרוג בתשלום. MFA יגן על החשבון האמיתי רק לאחר שתשלים את הרישום.
אסימוני התחברות והצמדה של היישומים עדיין נגישים ל־JavaScript במקור שלהם;
מעבר לשרת מתווך עם HttpOnly ופרוטוקול הצמדה קצר־חיים ונפרד לכל אתר נשארים
עבודה ארכיטקטונית נוספת. אין לראות בדוח אישור לאפס חולשות או בדיקת חדירה מלאה.
