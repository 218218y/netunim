# Storage V2 לאחר מעבר המחשבים הראשיים

עודכן ב־24 בספטמבר 2026. שני המחשבים הראשיים עברו ל־V2, רועננו לגרסת האתר עם writer v6, וסונכרנו זה מול זה לפי בדיקת המשתמש. מיגרציית `20260924120000_storage_writer_protocol_v2.sql` מותקנת בשרת. **ה־server fence הופעל לחשבון הפעיל** עבור Orders, קופה וצ׳קים משותפים. קריאה חוזרת מהשרת אישרה שלושה markers בערך 2, ללא restore פתוח וללא שינוי revisions בזמן ההפעלה. ה־revisions ברגע ההפעלה היו Orders 1451, קופה 434 וצ׳קים 118; הם צפויים להתקדם בשימוש רגיל.

ה־fence דוחה בשרת כתיבה למסמכי הליבה מ־RPC ישנים עד v5 או מ־UPDATE/INSERT ישיר של לקוח ישן. הלקוחות החדשים משתמשים ב־v6. בדיקות PostgreSQL מבודדות הוכיחו ש־v5 נכשל לאחר הפעלה, v6 ו־restore v6 עובדים, וחשבון אחר אינו מושפע. ה־fence אינו משדרג JavaScript שכבר פתוח בטאב ישן ואינו מנקה את האחסון המקומי שלו; הטאב הישן עשוי להציג נתונים מקומיים ישנים אך לא יוכל להחזיר את מסמכי הליבה בענן לאחור.

## מה קורה במכשיר חדש או ישן

התקנה נקייה נולדת כ־Local V2 ללא cloud cursor. אחרי התחברות יש לפתוח את החשבון הקיים **מהענן**. העברת `load-account` משתמשת ב־Main וב־Shared V2 מנותקים, מאמתת את ה־heads ורק אז מפעילה את owner של החשבון. ההתחברות כשלעצמה אינה הבטחה שהמסך כבר הציג את מצב הענן; יש להמתין לסטטוס מסונכרן ולאמת את נתוני Orders, קופה וצ׳קים לפני עריכה.

מכשיר משני שמכיל נתוני אתר ישנים אינו התקנה נקייה. המשתמש אישר שאין בו שינויים לא מסונכרנים שהוא מבקש לשמר. בגרסת האתר הבאה, דפדפן ללא marker של החשבון בודק את `get_storage_protocol_state` לפני שחזור או הצגת V1. אם השרת מסומן V2, הוא ננעל ומציג הוראה לטעינה מחדש מהענן; אם אין רשת או אימות מתאים, הוא נשאר נעול. טאב שכבר פתוח בגרסה ישנה מוגן על ידי ה־server fence, אך צריך לסגור אותו.

כדי להפעיל מכשיר משני ישן שבחרנו למחוק בו את העבודה המקומית:

1. סגרו בו את כל הטאבים של Orders והקופה. אל תבצעו זאת באחד משני המחשבים הראשיים.
2. מחקו **נתוני אתר** (LocalStorage, IndexedDB, Cache/Service Worker) של שני ה־origins בנפרד: `https://bargig-orders.pages.dev` ו־`https://bargig-kupa.pages.dev`. עבור `localhost:3000` יש לבצע זאת בנפרד רק אם נתוניו המקומיים אינם נחוצים. אל תמחקו קובצי JSON/גיבוי מחוץ לדפדפן.
3. פתחו את האתרים המעודכנים, התחברו לאותו חשבון ובחרו **פתיחה/טעינה מהענן**, לא ״העלה נתונים מקומיים״.
4. המתינו לסנכרון ובדקו את נתוני Orders, הקופה, הצ׳קים ואירועי הבנק לפני עריכה. אם מופיעה אזהרת DB לא תואם או מעבר תקוע, עצרו; אל תיצרו marker ידנית ואל תנקו את אחד המחשבים הראשיים.

## המשך הניקוי

השלב הנוכחי הוא release הגנה והסתגלות: server fence פעיל וגם gate בצד לקוח למכשירים ללא marker כבר נפרס. לאחר הפעלת ה־fence נבדקה שמירה בהזמנות ובקופה; סנכרון קופה למחשב השני ייבדק כשהוא יהיה זמין. תיקון המשך נועל את כתיבות ה־V1 כבר בזמן בדיקת הפרוטוקול, לפני תשובת השרת. לאחר CI ופריסת תיקון זה יש לוודא שוב שמירה וסנכרון A↔B ופתיחה של מכשיר משני לאחר ניקוי מכוון. עדיין אין למחוק את V1 באותו release שבו הופעלה החסימה.

עדכון מחבר האשראי v58 קיים בקוד אך טרם הותקן במחשבים. אין לפרוס את גרסת האתרים שדורשת v58 לפני התקנת `install_bank_bridge.bat` במחשבים שבהם משתמשים ברענון אשראי, אחרת הרענון ייחסם על ידי בדיקת הגרסה. שינוי זה אינו דורש SQL נוסף ואינו משנה את ה־server fence.

ב־cleanup הבא מסירים קודם writers עסקיים של V1 מ־production, ומשאירים לזמן מוגדר קוראים לקריאת מצב ישן או שחזור. לאחר מכן מפרידים את `checks` מ־Main V2 checkpoint/schema עם migration עמיד ואימות מול Shared. רק אחרי שכל המכשירים הידועים נטענו מהענן ותקופת שימוש תקינה, מסירים את קוראי V1, shadow/outboxes/`afterLegacy` ואת RPC ה־legacy הציבוריים. מחיקה של storage מקומי תהיה לפי מפתחות ידועים ובמכשיר שעבר אימות, ולא לפי wildcard של `.v1`.

אין לחזור על [runbook מעבר שני המחשבים](STORAGE_V2_TWO_COMPUTER_RUNBOOK.md); הוא תיעוד היסטורי. אם client חדש מציג `storage_protocol_upgrade_required`, יש לבדוק את גרסת האתר ו־Service Worker ואת ה־marker המקומי, ולא לכבות את ה־fence.
