# בנייה ופריסה של האתרים

תיקיות `netunim-orders/site` ו־`netunim-kupa/site` הן המקור לפיתוח. בניית הייצור יוצרת שתי חבילות עצמאיות, `dist/orders` ו־`dist/kupa`. רק החבילה הציבורית המאומתת מיועדת להעלאה. מפות המקור, הגרף, דוחות האימות והעתקי שחזור נשמרים תחת `.work/`.

## אימות וכניסה לסקריפט

```powershell
npm ci --ignore-scripts
npm run build
npm run build:check
```

| יעד | בדיקות מלאות במחשב | שימוש ב־CI של אותו commit |
| --- | --- | --- |
| שני האתרים | `deploy_all.bat` | `deploy_all_fast.bat` |
| Orders | `netunim-orders\deploy_site.bat` | `netunim-orders\deploy_site_fast.bat` |
| Kupa | `netunim-kupa\deploy_site.bat` | `netunim-kupa\deploy_site_fast.bat` |

כל הסקריפטים מקבלים `--preflight-only` לבדיקות ובנייה עד לפני ההעלאה. המסלול המהיר דורש Git, Python, Node/npm ו־`gh` מחובר. הוא דורש עץ נקי, כולל היעדר קבצים מוחרגים בתוך `site/`, והצלחה של **Full verification** בריצת **push** עבור ה־SHA המדויק. תוצאת PR על commit מיזוג זמני אינה אישור הפריסה של SHA אחר.

כל מסלול בודק את נכסי המקור, בונה את החבילה, מאמת את התוכן הציבורי ומפעיל את [שער Supabase](supabase.md#deployment-gate). אם יש מקור לאימות חי, נבדקת התאמת הסכימה מול השרת. אחרת נדרש אישור שמור מתאים. ההעלאה משתמשת בגרסת Wrangler מתוך [קובץ הגרסה](../../tools/wrangler-version.txt) ובעותק הקפוא של החבילה. פריסת אתר דורשת הרשאת Cloudflare לפרויקט המתאים.

## מה נשמר בכל העלאה

- החבילה הנבחרת נשמרת ב־`.work/releases/<app>/<release>/site`. לפני שימוש חוזר בדקו אותה עם `python tools/deployment-receipt.py verify orders <release>` או `kupa`.
- `.work/deployments/<app>` מכיל את ה־commit, מזהה החבילה, הפרויקט, תוצאת Wrangler וכתובות הפריסה שהחזיר. אם ההעלאה הצליחה ורישום האישור נכשל, בודקים את מצב הפרויקט לפני ניסיון נוסף.
- מפתח מטמון ה־PWA וכותרת `X-Netunim-Release` נקבעים מתוכן החבילה. ה־worker משתמש במטמון מעטפת של הגרסה שלו בלבד, ומאמת בנפרד את הבתים של נכסי ספק שנטענים לפי דרישה. עדכון ממתין עד לסגירת הלשוניות הישנות.

## סדר פריסה ושחזור

1. ודאו תאימות בין החבילות הנוכחיות, לקוחות ישנים וחוזי מסד הנתונים. שינוי ממשק מסד בלתי תואם מצריך שלב שרת תוספתי לפני עדכון הלקוחות.
2. הפריסה המשולבת בודקת את שני האתרים מראש ומעלה Orders ואז Kupa. לכל פרויקט היסטוריה משלו. אם העלאת Kupa נכשלה לאחר העלאת Orders, בדקו איזו גרסה פעילה בכל פרויקט והשלימו רק את האתר שנכשל מאותו commit מאומת.
3. אם דרוש rollback, בחרו את הפריסה הקודמת ב־Cloudflare בפרויקט המושפע, או אמתו והעלו את החבילה הקפואה הקודמת תחת גרסת Wrangler של המאגר. ודאו תאימות למסד לפני שימוש בחבילה ישנה. אין צורך באיפוס נתוני דפדפן או בהפעלה חוזרת של מיגרציה בשביל rollback של קבצים סטטיים.
4. אחרי ההעלאה בדקו התחברות, פעולה מייצגת, טעינה ללא רשת ופתיחה אחרי סגירת הלשוניות הישנות בדומיינים הקבועים. Wrangler מאשר קבלת חבילה. מסלול התעבורה הציבורי עשוי לשנות HTML או כותרות, ולכן בדיקת הבתים המדויקת מתבצעת ב־Preview מבודד.
