NETUNIM KUPA DEPLOYMENT
================================

Public root
-----------
Publish only netunim-kupa/site. Never serve the repository root, data/, backups/, SQL,
node_modules, credentials or source-only operational files. The public seed contains no business data.
index.html loads assets/app.js as native ESM; assets/js/main.js composes the application.
All assets/js modules, CSS, icons, manifest, service-worker.js, _headers and supabase/config.js are required.
Each site remains independently deployable and independently usable offline.

Preparation (repository root)
-----------------------------
Install the development dependencies described in TESTING.txt:
  python -m pip install -r tests/requirements.txt
  npm ci
After changing public/shared assets:
  python tools/sync-assets.py
  verify.bat --no-pause
Review all changes and preserve current operational backups before release.

Read-only preflight, no upload:
  netunim-kupa\deploy_site.bat --preflight-only
This runs the full repository verification and local deployment guards, then exits before
creating a Wrangler work directory or contacting Cloudflare. It does not clean public files automatically.
Unexpected files must be reviewed and removed explicitly.

Deployment (only when intentionally authorized):
  netunim-kupa\deploy_site.bat
The script re-runs the complete verifier, checks required modules/CSP/public-root safety,
then runs the Wrangler version managed in ..\tools\wrangler-version.txt in a fresh isolated temporary
directory. Only the absolute site/ path is uploaded. The configured Pages project is bargig-kupa.
Do not bypass the verification gate with a direct Wrangler upload.
From the repository root, check/update the deployment CLI deliberately with:
  npm run wrangler:check
  npm run wrangler:update
After changing the Wrangler version, run verify.bat --no-pause before deployment.

Deploy both applications together from the repository root:
  deploy_all.bat
This is the preferred paired release path: it runs the complete repository verifier exactly once,
then runs the full site-specific security/deployment guards and the centrally managed Wrangler version for
Orders and Kupa in sequence. If verification fails, neither upload starts; if an upload fails, the script
stops and does not start the next site. For a no-upload combined check use:
  deploy_all.bat --preflight-only
The individual deploy_site.bat files remain safe standalone entrypoints and still run verification
themselves. The shared tools/deploy_site_core.bat is an internal deployment engine, not the manual entrypoint.
No JavaScript build step or npm runtime dependencies are required.

Bank Hapoalim Bridge (local only)
--------------------------------
netunim-kupa/bank-bridge is a Windows-local companion and MUST NOT be uploaded to Cloudflare Pages.
The public site talks to it only through http://127.0.0.1:8765; Chrome can require Local Network Access permission.
Each workstation that may refresh Hapoalim installs its own bridge. The installer stages and validates a new runtime first,
then places it under %LOCALAPPDATA%\NetunimKupaBankBridge\app and installs an ASCII-only hidden Startup launcher.
The launcher resolves %LOCALAPPDATA% at runtime, so it is independent of the extracted repository path and safe when the Windows user/path contains Hebrew or other non-ASCII characters.
The bridge uses the workstation's installed Chrome/Edge with a dedicated local browser profile; Puppeteer's browser download is disabled.
Hapoalim credentials remain outside the repository and are encrypted with Windows DPAPI CurrentUser on each workstation.
The browser keeps only that workstation's random Bridge key and auto-refresh preference. Kupa/Supabase stores the resulting bank snapshot and shared successful bank-sync timestamp, never the Hapoalim password.
Deploying Kupa does not require installing the bridge on the deployment machine.

Cloud and security
------------------
supabase/config.js exports frozen public configuration. Only a publishable key belongs there;
never use a secret/service-role key. Keep its URL consistent with connect-src in _headers.
Supabase Auth and RLS control business-data access. A site access policy (for example Cloudflare
Access) is a separate layer controlling delivery of public application files. noindex is not authorization.
script-src forbids inline scripts/eval. Inline styles remain allowed only in style-src-attr;
style-src-elem is self-only. Existing object/base/frame, MIME, referrer and permission protections remain.

Ordinary frontend deployment requires no SQL/schema changes and must not rerun cutover.
For a genuinely new database, follow the existing setup and shared-check SQL documentation.
Never run migration SQL on production merely to publish frontend changes.

Offline and rollout checks
--------------------------
The worker precaches the full ESM dependency tree with a deterministic content-based cache version.
Text newlines are normalized for hashing across Windows/Linux checkouts; binary assets remain byte-exact.
Real public-content changes intentionally require running sync-assets.py so installed PWAs receive a new cache.
Only public shell assets are cached. Business snapshots and pending live in browser storage, not SW cache.
Offline lookup opens this release's named cache explicitly; another cache on the origin cannot supply shell files.
After release, check authorized login, a representative workflow, offline reload, recovery, folder permissions
and installed-PWA startup. Tests never contact production and do not replace this release check.
