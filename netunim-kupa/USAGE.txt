ניהול קופה — הוראות הפעלה ופיתוח
===============================

קובץ ההפעלה
------------
- מקור האפליקציה הפעיל הוא netunim-kupa/site/index.html.
- לפריסה מעלים רק את תיקיית site/.

עבודה באתר / PWA
----------------
1. פתח את האתר שהועלה.
2. התחבר ל-Supabase או בחר תיקייה מקומית בהתאם למצב העבודה.
3. נתוני קופה/בנק/אשראי/מזומן נשמרים ב-kupa_documents; הצ׳קים נשמרים במקור אמת נפרד shared_checks_documents.
4. יתרת הבנק היא צילום המקור הבנקאי (או צילום ידני). שינוי סטטוס של צ׳ק לעולם אינו מוסיף או גורע ממנה. bankEvents/depositSeq נשמרים רק כתאימות למאגר הצ׳קים הוותיק ואינם משתתפים בחישוב הכספי.

פיתוח מקומי
-----------
- משתמשים באותו site/index.html, אין גרסת HTML מקומית נפרדת.
- מומלץ להגיש את תיקיית site דרך http://localhost ב-Chrome/Edge.
- פתיחה ישירה ב-file:// אינה נתמכת: מודולי ESM ו-Service Worker דורשים HTTP(S)/localhost.
- משורש המאגר: python -m http.server 8081 --directory netunim-kupa/site
- לאחר מכן פתח http://localhost:8081. אין להגיש את שורש המאגר, המכיל קבצים שאינם מיועדים לפרסום.

עדכון יתרת בנק הפועלים
----------------------
- החיבור לבנק פועל דרך netunim-kupa/bank-bridge, שרץ מקומית ב-Windows ואינו חלק מתיקיית site המפורסמת.
- התקנה/שדרוג בכל מחשב: הפעל bank-bridge\install_bank_bridge.bat. ההתקנה מעתיקה את השירות לתיקייה קבועה תחת %LOCALAPPDATA% ומחליפה את מנגנון ההפעלה האוטומטית הישן. אין תלות במיקום תיקיית הפרויקט או בשם משתמש Windows בעברית.
- בסיום ההתקנה מפתח ה-Bridge של אותו מחשב מועתק ללוח. במסך בנק בקופה הדבק אותו, הזן קוד משתמש וסיסמה של הפועלים ושמור את החיבור.
- אם עובדים מכמה מחשבים, מתקינים ומגדירים את ה-Bridge פעם אחת בכל מחשב. לכל מחשב מפתח מקומי משלו; אין צורך שמפתחות המחשבים יהיו זהים.
- קוד המשתמש והסיסמה מוצפנים ב-Windows DPAPI למשתמש Windows הנוכחי ונשארים רק באותו מחשב. הם אינם נשמרים ב-Supabase, בקובץ הקופה, בגיבויים או ב-localStorage.
- היתרה, זמן הסנכרון המוצלח האחרון וכל התנועות שהבנק מחזיר בחלון המתגלגל של 30 הימים האחרונים (עד 1000 רשומות בבקשה) נשמרים כ-feed בנק מנורמל במצב הקופה המשותף. לכל תנועה נשמרת גם יתרת currentBalance שהפועלים מחזיר, ומוצגת כ״יתרה לאחר תנועה״ כאשר היא קיימת. לכן מחשב אחר שרואה את אותה קופה מציג את אותה תוצאת בנק ויודע אם כבר בוצע עדכון ב-24 השעות האחרונות.
- "רענן עכשיו" הוא ניסיון שקט ואינו פותח חלון בנק. אם הפועלים דורש אימות נוסף, לחץ "פתח אימות בבנק"; רק פעולה מפורשת זו פותחת Chrome/Edge גלוי. אחרי login מוצלח Bridge v10 ממתין ששירותי ה-SPA/API של הפועלים באמת יהיו מוכנים, בוחר את החשבון הרצוי וקורא קודם את היתרה; קריאת התנועות נעשית רק אחר כך ואינה יכולה לבטל יתרה שכבר נקראה בהצלחה.
- ניתן להפעיל עדכון אוטומטי פעם ב-24 שעות לפי זמן הסנכרון המוצלח האחרון מהבנק. הקופה צריכה להיות פתוחה; אם הייתה סגורה, הבדיקה נעשית בפתיחה הבאה. כישלון ברקע אינו משנה את היתרה הקיימת וניסיון חוזר מוגבל בזמן.
- ה-Bridge משתמש ב-Chrome או Edge שכבר מותקנים במחשב ובפרופיל מקומי ייעודי, ואינו מוריד Chromium נפרד של Puppeteer.
- Chrome עשוי לבקש פעם אחת הרשאת גישה לרשת המקומית עבור החיבור ל-127.0.0.1; יש לאשר אותה.
- אם יש כמה חשבונות תחת אותו משתמש, יש להזין גם סניף וגם מספר חשבון. בנק הפועלים מזוהה כבנק 12, ולכן לדוגמה סניף 123 וחשבון 456789 נשלחים ל-API כמזהה 12-123-456789. המערכת אינה מנחשת לפי סיומת של מספר חשבון ואינה מחברת יתרות.
- אם הבחירה חסרה/דו-משמעית, הקופה מציגה את רשימת החשבונות הפעילים שהפועלים החזיר (סניף + חשבון בלבד) ומאפשרת לבחור את החשבון המדויק בלי להקליד שוב את סיסמת הבנק.
- מסך הבנק מציג סימון של העדכון המוצלח האחרון, תאריך ושעה, ותנועות אחרונות. אם רק התנועות נכשלו, היתרה עדיין נשמרת ומוצגת אזהרה נפרדת.
- מבנה ה-feed הוא חוזה נתונים גרסאי שנועד לאפשר בהמשך גם לניהול הזמנות להציג ולעדכן את אותה תמונת בנק. החיבור של ניהול הזמנות עצמו אינו כלול בשלב זה.

תיקייה מקומית וגיבויים
----------------------
- site/index.html כולל את כל מנגנון בחירת התיקייה שהיה בגרסה המקומית הישנה.
- קובץ העבודה: data/kupa-data.json.
- גיבויים: backups/.
- שמות קובצי הנתונים/גיבויים/ייצוא נוצרים באנגלית בלבד (למשל kupa-data.json, kupa-backup_..., checks_..., credits_...).
- ה-handle נשמר ב-IndexedDB. אם נדרש אישור מחדש, ניתן לאשר את אותה תיקייה בלי לבחור אותה מחדש.
- ניתן לחבר גם תיקיית גיבוי נפרדת.
- עבודה בענן אינה תלויה בכך שהרשאת התיקייה המקומית פעילה בכל רגע.

Supabase
--------
- netunim-kupa/supabase/setup.sql — דומיין הקופה.
- netunim-orders/supabase/setup.sql — דומיין ניהול ההזמנות.
- netunim-orders/supabase/shared/setup.sql — דומיין הצ׳קים המשותף.
- cutover/preflight/postflight שבתיקיית shared הם כלי מעבר/בדיקה ולא מסלול עבודה יומיומי.

זהירות
------
- אל תנקה Site Data כאשר יש שינוי Offline שעדיין לא הסתנכרן.
- אל תעלה data/, backups/, SQL או קבצי הוראות לאתר הציבורי.
- אין לשים service_role/secret בקוד הדפדפן.

אם בנק הפועלים דורש קוד אימות, לחץ "פתח אימות בבנק". החלון נשאר פתוח עד 10 דקות וממשיך מיד לאחר שהאימות הושלם; אותו פרופיל Chrome/Edge נשמר בין ריצות ככל שהבנק מאפשר.

- Bridge v10 מזהה התחברות מוצלחת לפי סשן API מאומת של הפועלים ולא רק לפי כתובת URL. לאחר הצלחה הוא מנסה ברענונים הבאים להשתמש קודם בסשן השמור בפרופיל הדפדפן; אם הסשן פג, רענון שקט יחזיר בקשה לפתוח אימות במקום לסמן דף חשבון תקין כ-UNKNOWN_ERROR.

Bank Bridge v49 — אבחון נתוני שיקים ללא ניחוש

- פירוט נוסף מופעל רק כאשר תיאור הפעולה של הבנק עצמו מציין הפקדת שיק/שיקים. שמות מוטבים/מעבירים אינם משמשים לזיהוי, ולכן שמות שמכילים במקרה את האותיות "צק" אינם מסווגים עוד כשיק. "החזרת שיק" או חיוב רגיל מסוג "שיק" אינם הפקדת שיקים ואינם מקבלים חלונית הפקדה.
- בשורת תנועה של Hapoalim קיימים שני קישורי פירוט נפרדים: pfmDetails ו-details. החל מ-Bridge v48 הקופה קוראת אותם עבור תנועות שיק מזוהות: בהפקדה pfmDetails נשאר מקור לאסמכתת ההפקדה הכללית, ואילו details נקרא בנפרד לקבלת פירוט השיקים; בהחזרת שיק נשמרת האסמכתא המקורית של שורת הבנק ואינה מוחלפת במספר PFM. מידע מן details אינו רשאי להחליף אסמכתא סמכותית. הסכימה הציבורית עדיין אינה מבטיחה את מבנה טבלת השיקים/הצילום, ולכן שדות גנריים כמו transactionStatusCode=0, transactionSum=0, check=false או multiCheck=false אינם מוצגים כפרטי שיק.
- v46 שומר שדות label/value מקוננים בתוך שורת השיק עצמה, ולכן מספר שיק שמוחזר בתוך תא פנימי נשאר משויך לבנק/סניף/חשבון/סכום של אותה שורה. שיק יחיד בלבד רשאי להשתמש באסמכתת ההפקדה כמספר השיק כאשר אין מזהה נפרד; בהפקדה מרובת שיקים אין העתקה כזאת. מספרים שהבנק החזיר אך לא ניתן לשייך בבטחה לשורה מסוימת מוצגים בנפרד במקום לנחש התאמה.
- אם תשובת הבנק מכילה במפורש רשומות שיק מובנות עם סכום חיובי ובנק/סניף/חשבון ו/או מספר שיק, הן נשמרות ומוצגות כטבלה: בנק, סניף, חשבון, מס׳ שיק, סכום ומצב מסמך. לא נוצרים מספרי שיקים מערכי 0 או flags בוליאניים.
- כתובת צילום/מסמך, token, cookie, session או payload טכני אינם נשמרים ב-bank.feed ואינם עולים לענן. נשמר רק סימון שקיים מסמך, אם הבנק החזיר אותו במפורש.
- כשל בקריאת הפירוט הנוסף של הפקדה אינו מפיל את היתרה או את feed התנועות.

Bank Bridge v10 — יציבות ניווט בבנק הפועלים
-----------------------------------
החל מ-v10 קריאת יתרה ותנועות אינה מתחילה ברגע הראשון שבו דף החשבון נראה פתוח. ה-Bridge דורש חלון יציבות קצר של ה-SPA/API, ואם Puppeteer מאבד Execution Context בגלל redirect פנימי הוא ממתין לסשן מאומת ויציב ומנסה מחדש עד שלוש פעמים. שגיאות API אמיתיות אינן מוסתרות ואינן מקבלות retry אוטומטי.
במסך הקופה כפתורי הרענון, זמן העדכון האחרון וכשל העדכון האחרון נשארים גלויים; מפתח ה-Bridge, פרטי החשבון והעדכון האוטומטי נמצאים תחת 'הגדרות חיבור וסנכרון' הסגורות כברירת מחדל.

- אחסון תנועות הבנק: bank.feed הוא חלק ממצב הקופה. בכל שמירה נוצר גם עותק התאוששות מקומי בדפדפן (localStorage + IndexedDB). במצב Supabase אותו feed מסתנכרן למסמך הקופה בענן; במצב קובץ/תיקייה הוא נשמר בקובץ JSON.
- חלון התנועות הוא rolling של 30 יום. סנכרון מוצלח חדש מחליף את feed הקודם; תנועה שיצאה מטווח 30 הימים אינה נשמרת בארכיון ייעודי. אם נדרש היסטוריון קבוע לשיתוף עתידי עם ניהול הזמנות, יש לבנות מאגר bank-transactions נפרד ולא להגדיל ללא גבול את מסמך הקופה הראשי.


סנכרון חברות אשראי (Bank Bridge v18)
-----------------------------------
- מסך האשראי תומך בחיבור אוטומטי לכאל (Visa Cal), MAX, ישראכרט ו-American Express באמצעות אותו Bank Bridge מקומי. Mastercard אינו חיבור נפרד: מחברים את הכרטיס לפי החברה המנפיקה שלו.
- ניתן להגדיר כמה חיבורים לאותה חברה רק כאשר מדובר בזהויות כניסה שונות. אין ליצור חיבור נפרד לכל כרטיס של אותו בעל חשבון: חיבור אחד מגלה את כל הכרטיסים שהזהות מורשית לראות, וה-Bridge דוחה חיבור כפול לאותה זהות.
- כאל ו-MAX משתמשים בשם משתמש + סיסמה. ישראכרט ו-American Express משתמשים בתעודת זהות + 6 ספרות אחרונות של כרטיס מאותו סוג + סיסמה קבועה. אלו שני ספקים נפרדים עם base URL/company code נפרדים.
- החל מ-Bridge v42 ישראכרט ו-American Express משתמשים כברירת מחדל במסלול DigitalV3 דרך Chrome/Edge, המבוסס על upstream PR #1159 שנבדק מול חשבונות אמיתיים. Camoufox נשאר fallback מוגבל בלבד לכשלי HTML/WAF מוכחים; סיסמה שגויה לעולם אינה מפעילה דפדפן שני.
- החל מ-Bridge v41 מסלול Amex הראשי מותאם ל-upstream PR #1159 שנבדק end-to-end מול חשבון Amex אמיתי: Chrome/Edge מותקן, navigator.webdriver=undefined לפני הניווט, השהיה של 2.5–3 שניות לפני ValidateIdData, ולאחר login מעבר ל-DigitalV3 ב-web.americanexpress.co.il עבור כרטיסים, מסגרות ועסקאות. v39 של הזרקת client-hints נשאר היסטורי ואינו המסלול הפעיל.
- Bridge v41 מיישר גם את חוזה הכניסה בדיוק ל-PR #1159: ValidateIdDataBean.userName הוא שדה אופציונלי. כאשר Amex מחזירה returnCode=1 ללא userName, אין להמציא שם משתמש ואין לעצור כשגיאת schema; KodMishtamesh פשוט אינו נשלח ב-JSON של performLogonI, כפי שקורה ב-upstream.
- לאחר התקנת Bridge v42 יש להריץ מחדש install_bank_bridge.bat, משום שנוסף מודול DigitalV3 מקומי לישראכרט והאתרים דורשים Bridge v42 לפני סנכרון אשראי. הערת היסטוריה: v18 הסיר את מסנן טביעת-הדפדפן המקומי השגוי של v17 ונותן ל-Camoufox לייצר ולמפות את BrowserForge בעצמו דרך os/screen הנתמכים. אימות הסשן מתבצע בפועל מול דף הכניסה האנונימי לפני שליחת תעודת זהות/6 ספרות/סיסמה, ו-fingerprint-generator נשאר מקובע לגרסה 2.1.86. בהתקנה ראשונה Camoufox יורד אל %LOCALAPPDATA%\NetunimKupaBankBridge\camoufox ולכן היא יכולה לקחת יותר זמן.
- אם fallback של Camoufox מקבל 403 בדף הכניסה האנונימי, רק Camoufox נכנס ל-cooldown של 24 שעות; Chrome/Edge אינו נחסם על סמך 403 של מנוע אחר. לאחר תום ההשהיה זהות Camoufox שנדחתה מוחלפת פעם אחת לפני fallback זכאי. HTTP 429 נשאר חסם ספק כללי ומכבד Retry-After.
- כל חיבור יכול להחזיר כמה כרטיסים. לכל כרטיס ניתן לקבוע בנפרד כלול/לא כלול, גלוי/מוסתר, עסקי/ביתי ושם תצוגה. כרטיס מוסתר שכלול בחישוב ממשיך להיכנס לסכומים אך אינו מוצג כפירוט מזוהה.
- ניתן לסנן את הסיכומים והפירוט לפי עסקי/ביתי ובמקביל לפי בעל הכרטיס, כך שאפשר להציג לדוגמה רק עסקי של בעל מסוים או את כל הכרטיסים שלו.
- סנכרון מלא מבקש 130 יום אחורה ועד 12 חודשים קדימה, ללא איחוד תשלומים, כדי להשתמש בתאריכי החיוב והתשלומים שהחברה עצמה מחזירה. עסקאות ממתינות מוצגות מיד באזור נפרד "עסקאות ממתינות", אך אינן נכנסות לתחזית/קופה עד שהחברה מחזירה חיוב סופי עם מועד אמין.
- היסטוריית האשראי שנשמרת באפליקציה כוללת עד 12 חודשי חיוב קודמים. השמירה הזו נצברת בהדרגה מסנכרונים רגילים ואינה גורמת למשיכה יזומה של 12 חודשים אחורה; רענון מלא ממשיך לבקש 130 יום אחורה בלבד, וכאשר נצברים יותר מ-12 חודשים החודש הישן ביותר נחתך.
- MAX מחזירה CreditLimit ו-OpenToBuy, וישראכרט/Amex v42 מקבלים creditLimitAmount + limitUsed מ-DigitalV3; במסלולים אלה נתון המסגרת הפנויה של החברה הוא הסמכותי וכבר כולל את הניצול/האישורים שהחברה מכירה, ולכן לא מפחיתים pending פעם נוספת. כאל מחזירה מסגרת כוללת אך לא OpenToBuy אמין בחוזה הנוכחי; כאשר אין availableCredit ישיר, החישוב המקומי מפחית גם חיובים עתידיים סופיים וגם אישורים ממתינים שקליים.
- נתוני החברות הם מקור האשראי הראשי. אין מתג בין מצב ידני למסונכרן; הוספת סליקה ידנית נשארת כתוספת נקודתית בלבד. במעבר הראשון ל-credit feed v3 הנתונים הידניים ההיסטוריים נמחקים פעם אחת כדי שלא ייספרו פעמיים, ותוספות ידניות חדשות נשמרות לאחר מכן.
- נתוני העסקאות המסונכרנים והשיוכים נשמרים במצב הקופה ומסתנכרנים לענן כמו יתר נתוני הקופה. סיסמאות, תעודות זהות ושמות משתמש אינם חלק ממצב הקופה ואינם נשלחים ל-Supabase; פרטי הכניסה נשמרים מוצפנים ב-Windows DPAPI בכל מחשב בנפרד.
- אפשר להפעיל רענון אוטומטי פעם ב-24 שעות. חיבורים מקומיים מסונכרנים סדרתית כדי למנוע ערבוב sessions בין זהויות באותה חברת אשראי.
- „איפוס מלא” מוחק את כל פרופילי האשראי המוצפנים מהמחשב ומנקה את state.creditSync דרך מסלול השמירה הרגיל, ולכן גם את נתוני הסנכרון בענן. תוספות ידניות שנוצרו אחרי מעבר v3 אינן נמחקות באיפוס הסנכרון.
- מחיקה רגילה של חיבור היא מקומית בלבד. לכן פרופיל שכבר סונכרן יכול להמשיך להופיע כ„הגדר גם במחשב זה” במחשב אחר; משתמשים ב„איפוס מלא” כשרוצים להתחיל מאפס בכל נתוני הסנכרון.
- שגיאות HTML/WAF מסווגות לקודים בטוחים בלי לשמור raw HTML או payload של בקשת ההתחברות. מסלול Camoufox משתמש ב-CREDIT_AUTOMATION_BLOCKED, CREDIT_LOGIN_HTML_RESPONSE ו-CREDIT_DATA_HTML_RESPONSE; v18 שומר גם על ההפרדה CREDIT_PROVIDER_RATE_LIMITED עבור HTTP 429 כדי שלא לבצע retry שגוי.

Credit feed v3 — בחירת כרטיסים וסיכום חודשי
- חיבור לחברה מגלה את כל הכרטיסים שהזהות מורשית לראות. גילוי כרטיס אינו אישור לכלול אותו בחישובי הקופה; כרטיס חדש אינו נכנס לחישוב עד בחירה מפורשת.
- לכל כרטיס יש הגדרות עצמאיות של כלול/לא כלול, גלוי/מוסתר, עסקי/ביתי ושם תצוגה. רק כרטיסים כלולים נכנסים לתחזית; מוסתר משפיע על התצוגה בלבד.
- תצוגת הנתונים המסונכרנים כוללת סיכום לפי חודש וכרטיס, סה"כ חודשי וכללי, מסנני בעלים + עסקי/ביתי, וטבלת עסקאות/תשלומים מאוחדת עם התקדמות ותשלום הבא כאשר נתוני החברה מאפשרים זאת.
- American Express נשאר ספק נפרד עם company/base URL משלו. מסלול ההתחברות הקבועה הוא API-driven (ValidateIdData ואז performLogonI), ולכן אין להסיק ממצב הטופס החזותי אם ההתחברות הצליחה; תוצאת ה-Bridge היא מקור האמת.

- Bridge v48 שומר עבור 'החזרת שיק' ו-'הצ שיק חוזר-נט' את שורת השיק מתוך פירוט ה-details שהבנק עצמו מציג. שדות contra* של שורת העו״ש אינם משמשים עוד ליצירת שיק נוסף, ולכן אינם יכולים ליצור שורה כפולה או חשבון שגוי. ב'החזרת שיק' בלבד אסמכתת שורת העו״ש יכולה לשמש fallback למספר השיק כשיש שורת שיק יחידה; ב'הצ שיק חוזר-נט' האסמכתא הכללית לעולם אינה מועתקת למספר השיק בלי הוכחה מפירוט ה-details. תנועות אלה אינן מסומנות כהפקדת שיק.


- ב-Bridge v49 נוספה בתוך „אפשרויות סינכרון” פעולה „ייצוא אבחון שיקים (TXT)”. אחרי רענון בנק היא מורידה קובץ מקומי שמכיל רק תנועות שהפועלים זיהה כתנועות שיק, יחד עם שמות השדות והערכים המסוננים של שורת העו״ש ושל תגובות pfmDetails/details לפני ואחרי הנרמול. הקובץ אינו נשמר בענן ואינו נכנס לגיבויים. סיסמה, קוד משתמש, cookies, authorization/session/XSRF tokens, HTML ותמונות/מסמכים בינאריים מושחרים; accountId בכתובות מושחר גם הוא. הקובץ עדיין יכול להכיל סכומים, אסמכתאות ופרטי שיק ולכן יש לשתף אותו רק במכוון. אם עדיין לא בוצע רענון עם v49, הייצוא יבקש לבצע רענון תחילה.

Bank Bridge v50 cheque identity
-------------------------------
The bank's authenticated cheque-details response supplies the printed cheque number in
`details.list[].number`. v50 reads that field directly for all completed cheque detail
rows, including multi-cheque deposits and returned-cheque credits. Aggregate transaction
references are not copied into cheque-number fields.

Bank Bridge v51 bank diagnostics
--------------------------------
- „ייצוא אבחון בנק (JSON)” מייצא את הסנכרון האחרון כ-JSON מקומי ומובנה ולא כ-TXT של שיקים בלבד.
- לכל חשבון נשמרות עד 500 התנועות החדשות ביותר מכל הסוגים, כולל זיכויים/העברות, חיובים, שיקים ושאר הפעילויות שהבנק החזיר. אם היו יותר תנועות, השדה `truncated` מציג כמה לא נכנסו לקובץ.
- בכל תנועה מופיעים זה לצד זה `rawTransaction` של הפועלים ו-`normalizedTransaction` של Netunim. בנוסף קיימים `activitySummary` ו-`fieldInventory`, כדי לזהות אסמכתאות ושדות חשובים שהבנק שולח אך הממשק עדיין אינו מציג.
- בתנועות שיק נשאר גם פירוט `pfmDetails/details` לפני ואחרי הנרמול. מזהי/תוכן תמונה עצמם אינם מיוצאים; נתיבי front/back נשמרים רק בצורה מסוננת בלי accountId/session/token לצורך אבחון מבנה מסמכי הבנק.
- הקובץ נשאר במחשב בלבד ואינו עולה ל-Supabase, לארכיון הבנק או לגיבויים. הוא עדיין מכיל מידע פיננסי ולכן משתפים אותו רק במכוון.


Bank Bridge v52 cheque images
-----------------------------
- Hapoalim cheque detail rows expose session-scoped `imageFrontLink` / `imageBackLink`. v52 downloads those bytes only while the authenticated bank session is alive; the original bank URL, accountId, cookies and session values are never written to cloud state.
- The Bridge keeps a bounded local 183-day (about six-month) cache and exposes an image only through the authenticated loopback endpoint by an opaque SHA-256 key. A failed image fetch is non-fatal and never invalidates the bank balance or transaction sync.
- Supabase stores the binary objects in the private `bank-cheque-images` bucket. Bank rows keep only small `imageFrontKey` / `imageBackKey` values; image bytes are not embedded in Postgres JSON, Kupa/Orders documents or their application backups.
- Cloud retention is 183 calendar days (about six months). Because the ordinary bank sync fetches a 30-day transaction window, the first run can populate only the images that Hapoalim still exposes; continued daily/periodic sync gradually builds the rolling 183-day window.
- Expired image objects are deleted through the Storage API during later bank syncs. The historical bank transaction remains; only its image becomes unavailable after retention.
- The bucket is private and RLS-scoped to the authenticated user's top-level folder. Objects are immutable (`x-upsert:false`), so no UPDATE policy is granted.
- The UI downloads the original image lazily only when the user presses חזית/גב. v52 does not call Supabase Image Transformations and does not require that project option to be enabled.
