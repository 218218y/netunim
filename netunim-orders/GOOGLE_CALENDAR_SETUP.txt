ניהול הזמנות — חיבור Google Calendar
=====================================

עקרון העבודה
------------
Google Calendar הוא מקור האמת היחיד ליומן. המערכת אינה מעתיקה את היומן למסמך Supabase ואינה מנהלת יומן עסקי שני.
בדפדפן נשמרים רק:
- מטמון תצוגה של טווחי תאריכים שכבר נטענו, כדי שאפשר יהיה לראות אותם גם באופליין.
- תור פעולות שלא קיבלו עדיין אישור מ-Google. התור נשמר ב-IndexedDB לפני שהחלון נסגר ולפני ניסיון השליחה.

יצירת אירוע מקבלת מזהה Google תקין מראש. אם Google שמר אירוע אבל תשובת הרשת אבדה, ניסיון חוזר משתמש באותו מזהה ולכן אינו יוצר תור כפול.
עדכון חוזר הוא idempotent מבחינת השדות שהמערכת מנהלת, ומחיקה שכבר בוצעה נחשבת הצלחה גם אם Google מחזיר 404 בניסיון חוזר.

הגדרה חד-פעמית ב-Google Cloud
------------------------------
1. פתח Google Cloud Console ובחר/צור Project ייעודי.
2. הפעל את Google Calendar API.
3. הגדר OAuth consent screen. אם האפליקציה נשארת במצב Testing, Google מאפשרת התחברות רק לחשבונות שהוגדרו כבודקים:
   - פתח Google Auth Platform > Audience.
   - ודא ש-Publishing status הוא Testing.
   - תחת Test users לחץ Add users והוסף את כתובת ה-Google המדויקת שממנה מתחברים ליומן.
   - שמור, סגור חלון OAuth ישן אם הוא פתוח ונסה להתחבר מחדש.
   שגיאה 403 access_denied עם הודעה שהאפליקציה בבדיקה אינה תקלה בקוד או ב-COOP; היא אומרת שהחשבון שנבחר אינו מורשה כ-Test user (או שמדיניות החשבון/הארגון חוסמת אותו). לשימוש פרטי/במספר קטן של חשבונות אפשר להשאיר את האפליקציה ב-Testing ולהוסיף אותם כ-Test users; אין צורך לעקוף את מנגנון ההרשאה בקוד.
4. ב-Google Auth Platform > Data Access ודא ששני ה-scopes שהקוד מבקש מופיעים בהגדרת האפליקציה:
   - https://www.googleapis.com/auth/calendar.events
   - https://www.googleapis.com/auth/calendar.calendarlist.readonly
5. צור OAuth Client ID מסוג Web application.
6. תחת Authorized JavaScript origins הוסף את כל ה-origins שמהם המערכת מופעלת, לדוגמה:
   - כתובת האתר האמיתית של ניהול ההזמנות, בלי נתיב בסוף.
   - http://localhost:8082 לפיתוח מקומי אם משתמשים בפקודה שמופיעה ב-USAGE.txt.
   אם קיימים דומיין מותאם וגם כתובת pages.dev, הוסף את שניהם רק אם שניהם משמשים בפועל.
6. אין צורך ב-Client Secret בדפדפן, ואין להכניס Client Secret לקוד.

חיבור הקוד
----------
פתח:
  netunim-orders/site/assets/js/calendar/config.js

החלף את:
  PASTE_GOOGLE_OAUTH_CLIENT_ID.apps.googleusercontent.com

ב-OAuth Client ID שקיבלת מ-Google, והשאר את scope כפי שהוא. ה-scope מוגבל לעריכת אירועים בכל היומנים ולקריאת רשימת היומנים; הוא אינו מעניק למערכת הרשאות לשתף או למחוק יומנים עצמם.

לאחר שינוי הקובץ הרץ משורש המאגר:
  python tools/sync-assets.py
  verify.bat --no-pause

שימוש
-----
1. פתח את ניהול ההזמנות ועבור לטאב "יומן".
2. לחץ "התחבר ל-Google" ואשר גישה ליומן. אם Google מציגה 403 access_denied בנוסח "האפליקציה נמצאת כרגע בבדיקה", חזור ל-Google Auth Platform > Audience והוסף את החשבון שמופיע בחלון כ-Test user. אזהרות console מסוג Cross-Origin-Opener-Policy על window.closed אינן הסיבה ל-403 הזה; כותרת האתר צריכה להישאר Cross-Origin-Opener-Policy: same-origin-allow-popups.
3. המערכת קוראת את כל רשימת היומנים בחשבון, כולל יומנים מוסתרים, ואת האירועים בטווח המוצג. בלי סינון eventTypes, Google מחזיר גם אירועי יום הולדת וסוגי אירועים נוספים שה-API מציג. יומן שנותן רק הרשאת free/busy נשאר ברשימה אך אינו נקרא כאילו יש הרשאה לפרטי אירועים.
4. אירועים רגילים ביומן עם הרשאת owner/writer ניתנים לעריכה.
5. אירועי יום הולדת, אירועים נעולים, יומנים לקריאה בלבד ואירועים עם מוזמנים מוצגים אך לא נערכים במסך הזה, כדי למנוע שינוי לא בטוח של מידע ש-Google מנהל או של התראות למוזמנים.
6. "תור חדש" נוצר ביומן הראשי/הראשון עם הרשאת כתיבה.

אופליין והתאוששות
-----------------
- שמירה/עריכה/מחיקה נכתבות קודם לתור IndexedDB המקומי ורק אחר כך נשלחות לרשת.
- אם אין רשת, השינוי נשאר מסומן כממתין ולא נעלם אחרי רענון/סגירת הדפדפן.
- כשחוזרת רשת, המערכת מנסה לשלוח שוב אוטומטית כל עוד קיים Access Token תקף.
- Access Token של Google אינו נשמר ב-localStorage או IndexedDB. אחרי רענון מלא/פתיחה חדשה ייתכן שתידרש לחיצה נוספת על "התחבר ל-Google". השינויים הממתינים נשארים שמורים עד אז.
- אם מנסים להתחבר לחשבון Google אחר בזמן שקיימים שינויים ממתינים לחשבון הקודם, הסנכרון נעצר ולא שולח אותם לחשבון הלא נכון.
- אין לנקות Site Data כאשר בטאב היומן מופיעים שינויים ממתינים.

אבטחה
------
- OAuth Client ID הוא מזהה ציבורי ומותר בדפדפן; Client Secret אסור בפרויקט הציבורי.
- Access Token נשמר בזיכרון בלבד.
- _headers מאפשר את נתיבי Google Identity Services הנדרשים, את www.googleapis.com ואת COOP המתאים לחלון OAuth, בנוסף ליעדים שכבר היו מותרים.
- Service Worker אינו מיירט או מטמין בקשות Google; בקשות cross-origin עוקפות אותו.
