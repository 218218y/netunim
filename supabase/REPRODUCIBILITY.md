# Canonical reconstruction and retention infrastructure

The sole application database installation chain is the ordered SQL under
`supabase/migrations/`. `canonical-migrations.json` and
`canonical-migration-manifest.json` are **local reviewed expectations**, generated
by `python tools/supabase_migration_manifest.py --write`. They are not evidence that
a migration has run. `supabase_postflight.py` independently checks live server
versions, names and recorded SQL hashes against these files and the files' own
hashes. A pending migration blocks deployment. Never regenerate expectations from
an unexplained live drift.

## What the earlier baseline omitted

The first four migrations reconstructed application schemas, functions, indexes,
ACLs, policies and triggers. They included both internal prune function definitions,
but omitted pg_cron installation and scheduling metadata. The two Production jobs
had been created by historical upgrades; those files are archived reference, not
installation prerequisites. `retention_cron_jobs` closes that omission in the
canonical chain. Its timestamp is generated by the Supabase tooling, not handwritten.

The migration enables pg_cron and creates missing jobs using its scheduling API.
An existing exact job is a no-op (including its job ID). A single owned job with a
changed schedule, command or active flag is updated in place using `cron.alter_job`.
Duplicate names, aliases invoking retention, foreign ownership/database or an
unexpected connection target raise an exception. They are never silently removed.
An advisory transaction lock serializes migration reruns; pg_cron's unique
name/owner constraint also protects named-job creation. The complete retention set
is rechecked before completion. Supabase does not grant postgres direct table-lock
access to its extension table, so the migration uses supported APIs without changing
extension privileges. Concurrent external edits are checked by postflight. No prune
function is called and no application table is read or written by this migration.

The postflight reads the full cron catalog with an RLS-bypassing operator, then
requires pg_cron, an enabled scheduler in GMT, and exactly the two expected
retention jobs from `retention-jobs.json`. It checks names, schedules, command text,
active state, owner, database and local connection target/port. It detects aliases
by retention names and prune function references; unrelated jobs remain allowed.
Missing catalogs/access fail closed, as do missing operational capture fields.
For database releases, the live postflight remains authoritative. Static site uploads
use `production-deployment-receipt.json` as a mandatory offline dependency gate: the
local schema snapshot, migration SQL hashes and retention contract must still match the
last authenticated Production postflight. This prevents a frontend deploy from outrunning
an unapplied migration without requiring database credentials on every workstation.
When a connector capture or PostgreSQL connection is configured, the deployment engine
also runs the stronger live drift check before upload. A database-contract change always
invalidates the receipt gate until a new live Production verification is recorded.

## Historical normalization is provenance, not a prerequisite

On 2026-09-06 the seven exported legacy ledger rows were replaced by the baseline
marker using the guarded metadata-only `audit/normalize-migration-history.sql`.
The baseline SQL was subsequently stored as text in its ledger `statements`, without
executing it on populated Production. That text is independently verified by its
server hash against the canonical baseline file. Original metadata, including
statements, remains in `audit/original-full-migration-history.json`.

A new database needs none of those metadata operations. The migration runner
executes the baseline and subsequent files in order and records them normally.
Do **not** run the normalization audit SQL or `migration repair` on a fresh database,
and do not replay the baseline on existing Production. The original SQL Editor/MCP
history is not an input to reconstruction. This followup only applies a new migration
normally; it does not repair, delete or rewrite any existing migration history.

No installation SQL needs to be copied from RELEASE.md. The historical review's
normalization steps describe an already completed one-time transition, not a
current runbook. Further schema/operational changes require new versioned migrations.

## Scope and verification limits

Reconstruction assumes the Supabase platform prerequisites: managed roles/auth
schema, extensions available to install, PostgreSQL with the pg_cron worker
preloaded in database `postgres`, and a privileged migration operator `postgres`.
The platform supplies these; application migrations do not install server binaries
or reproduce Supabase Auth settings, secrets, Edge Functions, business rows or
historical job-run logs. UTC/GMT scheduling and the active worker setting are
checked rather than silently changed by application SQL.

`tests/supabase_baseline.py`, `tests/supabase_candidate.py` and
`tests/supabase_retention.py` replay the complete chain on a new disposable
PostgreSQL database with minimal Supabase roles/auth fixtures. On Windows the cron
API/catalog is explicitly modeled because the native extension is unavailable.
Tests prove fresh job creation, exact contents, rerun ID stability, in-place repair,
atomic rejection of ambiguous jobs, and that direct prune calls would fail the
migration. Negative tests exercise the real postflight executable. The actual live
gate must reject this Windows fixture's absent extension; synthetic positive
captures stay in disposable test directories and are never deployment evidence.

Real pg_cron installation on a fresh Supabase platform is not certified by that
model. This workstation's Ubuntu WSL cannot start (HCS_E_SERVICE_NOT_AVAILABLE),
and Docker is unavailable. Production verification independently checks its real
extension/catalog after the migration. No scheduler/prune execution is triggered
for testing. See the dated retention audit for actual server evidence.

The ten intentional SECURITY DEFINER RPC warnings and their two-user regression
coverage remain unchanged; see REVIEW.md. No privilege/security-mode changes are
part of this followup.
