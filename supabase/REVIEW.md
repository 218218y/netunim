  upgrade files, hashes, 15 identical Kupa copies, isolated replay effects and reviewed
  feature evidence. No business rows or data-backfill completion were inspected.

Catalog comparison ignores only ACL/list ordering, CRLF/LF, and PostgreSQL 18's extra
NOT NULL catalog rows (the same NOT NULL invariant is checked in columns). It checks
full function definitions, owner/security mode/search_path, grants and grantors,
sequence definitions/ownership, policies, indexes, constraints and triggers. Sequence
limits are strings to preserve bigint precision; current sequence values are excluded.

## Canonical migrations

Versions below were generated by `supabase migration new`, not invented:

1. `20260906200304_production_schema_baseline.sql`: schema-only reconstruction of the
   observed application state. Fresh-install use only. It deliberately retains the
   observed security settings and function bodies; this is not an upgrade to run on
   a populated Production schema. Generate with `tools/build_schema_baseline.py`.
2. `20260906203818_capabilities_security_invoker.sql`: make the metadata-only capability
   RPC SECURITY INVOKER, preserving authenticated/service_role access and denying anon.
3. `20260906203827_restore_group_qualified_owner_updates.sql`: qualify owner/group
   predicates in `apply_restore_group_v5`. Production has
   `plpgsql.variable_conflict=error`; its baseline definition fails when updating a
   restore phase because `restore_group_id` is also an OUT parameter. A second failure
   occurs for restores without checks: an unassigned record is referenced through a
   CASE expression. An explicit IF avoids resolving that record in the absent branch.
   Both changes preserve owner filtering, snapshots and atomic restore behavior.
4. `20260906203837_oauth_owner_index.sql`: add the missing OAuth owner FK lookup
   index, with a one-second lock acquisition limit and 30-second statement limit.
   The observed table occupied 49,152 bytes. Transactional CREATE INDEX succeeded;
   no business rows were rewritten. These three deployed versions were generated by
   `apply_migration`, replacing the provisional CLI-generated filenames locally.

New schema work belongs only in this root `supabase/migrations/` directory. Existing
setup/upgrade files remain historical references and test fixtures, not an alternative
deployment chain. Do not run all upgrades or execute the baseline against Production.

entrypoints deny anon. `service_role` execution is explicitly present but still needs a
user identity for owner-scoped operations. The two internal helpers are authenticated
only (plus their owner), because invoker save RPCs use them.

Finance wrappers call `netunim_internal.assert_finance_sync_fence` before their private
implementations. Both the helper and every `fenced_impl_*` are unavailable to anon and
authenticated directly. The owner guard is not assumed merely from a public wrapper's
text: the helper/internal definitions and real two-user calls are checked.

`tests/supabase_authorization.py` covers all 13 rows, null JWT identity, anon, positive
owner paths and equality of **all** A-owned application rows after B's requests.
`tests/finance_fencing_server.sql` also covers expiry, takeover and wrong epoch.
The dynamic SQL in the non-client retention function uses internal table identifiers;
the RLS event trigger uses PostgreSQL DDL event object identities, not RPC input.

## Postflight and review sequence

`tools/supabase_postflight.py` reads live catalogs in a read-only transaction and compares
them plus migration history to the reviewed Production artifacts. The actual site upload
path always checks the last authenticated Production receipt before Wrangler.
`--preflight-only` checks static files and that same receipt, then stops without a
cloud connection. Pending database migrations therefore block preflight as well
as upload. When live PostgreSQL access is configured, failed access or drift also
blocks upload.
Use PGHOST/PGPORT/PGDATABASE/PGUSER and a passfile or service; never place secrets in SQL
artifacts or command arguments. A connector capture can also be compared with
`--actual <inventory.json> --history <migration-list.json>` during review.

For an authenticated connector/CI job that already read the live catalogs, deployment
also accepts `NETUNIM_SUPABASE_CAPTURE` (or `--capture`). This operator handoff contains
the known `project_id`, server `captured_at`, complete `inventory`, `migrations`, and
the server SQL-hash `manifest`, plus `build_fingerprint()` from the postflight module.
It is accepted for at most five
minutes and only for the exact current public assets/migrations/expectations. The
same full schema and ledger comparison still runs. This is trusted local operator
evidence, not a signed attestation; never construct it from old audit snapshots.
Expired evidence, another project, a changed build, modified recorded migration SQL,
or any schema/history drift blocks upload.

After reviewing this exact diff and confirming the target environment:

5. Re-run live postflight and Advisor. Ten intentional public DEFINER warnings should
